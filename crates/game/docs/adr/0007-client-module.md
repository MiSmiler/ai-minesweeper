# Client module: the frontend input pipeline behind one interface

The frontend is a client module — one module that owns the browser's view of the game. Created with the Board and top-bar elements (the counter, the Smiley Button, the Timer, and the difficulty row) and the state/action functions (`fetchState`/`post`), it exposes a small interface — `init` (fetch and render the initial state), `handleInput` (an abstract input event: a kind plus the Cell under the pointer, or none off-Board), `newGame` (with an optional difficulty), and `pollTimer` — and hides everything else behind it: the cached game state, the gesture machine (ADR-0005), the action controller (which drops stale responses so only the latest action's result ever renders), the preview highlight layer (whose retain/release brackets Reveal/Chord round trips so the Cells do not flash back to Hidden, issue #32), the Smiley Button's faces (including the surprise face while a press is held), end-of-game cancellation (a response that flips the game to Won/Lost cancels an in-progress gesture, issue #50), and the 1-second Timer poll.

The seam is real because two adapters satisfy it: the browser DOM and the test harness. Input crosses the seam as abstract events so tests drive the module without a DOM at the input edge; rendering crosses it as injected element references, so the top-bar renderer performs no hidden document lookups. The bootstrap is a thin DOM adapter — listener registration, hit-testing, pointer-move throttling, and difficulty/Smiley click delegation — just as the server layer is a thin adapter over the core (ADR-0003).

The module replaces coordination glue that previously lived in the bootstrap script with no interface and no tests — exactly where the preview-flash (issue #32), end-game race (issue #50), and Smiley-surprise bugs lived. Its interface is its test surface: the coordination rules (retain/release, end-of-game cancellation, surprise face, new-game paths, Timer-only poll, stale-response dropping) are covered by tests that observe only the rendered DOM and the sent actions. ADR-0005's purity claim is untouched: the gesture machine stays a pure function of (event, game state) behind the module.

Deliberately deferred: shrinking the gesture machine's per-event interface. Today the module builds the machine's hit payload (Preview scope, Revealed-ness, numeric-ness) from its cached state because the machine's seam accepts only the game-state name; letting the machine derive that payload from the full game state would fold the caller-side rule set behind the machine's interface. It is future work, not part of this seam — a future architecture review should not re-suggest it as a defect of the client module.
