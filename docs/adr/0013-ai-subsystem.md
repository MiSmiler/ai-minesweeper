# AI subsystem: a core-decoupled generic agent runtime with a Minesweeper binding adapter

The AI feature set — the `AiHelpMePlay` advisor mode now, and the future `AiPlay` / `AiPlayWithMe` modes — is organized as two layers rather than as `assist`-flavored modules inside `core` or `server`. `src/ai/` is a generic agent runtime that is deliberately decoupled from the core game: it knows nothing about Minesweeper, reuses nothing from `core`, and exposes only a `Tool` abstraction, a `Session` / message-history, a `Provider` seam, and a `run_loop`. `src/ai_adapter/` is the Minesweeper binding that depends on both `core` and `ai`: it renders the board into the #94 presentation forms, builds the system prompt, and wraps `core`'s `reveal` / `toggle_flag` / `chord` into `ai::Tool`s. `server` stays a thin transport layer that owns the `/ai/...` SSE routes and calls into `ai_adapter`; `ai_adapter` never depends on `server`, and `main` composes everything (build the `Game`, build the `ai` agent, register the tools via `ai_adapter`, wire the routes).

Inside `ai`, the runtime splits into `agent` (the engine: `Agent`, `Tool`, `Session`, `run_loop`) which depends on `provider` (the `Provider` seam plus concrete impls — currently DeepSeek as `deepseek`), so `agent → provider` is the only internal dependency and `provider` depends on nothing internal. The `Provider` seam exists because more providers than DeepSeek are expected; the DeepSeek impl carries the HTTP/SSE streaming, `tool_use`, and `image_url`/vision specifics.

The one-shot advisor mode (issue #91's "AI 看我玩") is `ai_adapter::suggest()`: single-turn, read-only, it injects the board and returns one analysis plus a suggestion. It is *not* named `assist` — that was only a working term in the issue discussion, not a code or doc symbol. The AI emits the `SUGGEST {"row":N,"col":M}` line (or `SUGGEST null`) per the #94/#95 prompt contract; that token stays exactly as decided there and is unconsumed — reported but never parsed. The future persistent-loop mode (`AiPlay`) is `ai_play` and will run a tool loop that reads and writes the `Game`; its name is provisional.

Tool binding is a parameter, not a hardcoded single game: `ai_adapter::tools` builds the `ai::Tool`s from a `GameHandle` passed in. Today every mode shares the backend's single `Game` (`Arc<Mutex<Game>>`) and switching modes triggers a new game; the future `AiPlayWithMe` mode needs two Game instances — binding tools to a handle keeps the adapter unchanged for that.

Considered options: a single file for the advisor mode was rejected — it would become a god file and leave no seam for the future loop; a separate crate now was rejected — the AI boundary is still evolving and, because `ai` is core-decoupled, promoting it to a crate later is a mechanical move, with no publish/versioning need yet; making `ai` depend on `core` was rejected — that is what would make a later crate extraction expensive; skipping the `Provider` seam was rejected — it would couple the runtime to DeepSeek; housing the one-shot mode inside `server` was rejected — the shared board / prompt / tools belong to the subsystem, not to a transport layer.

Consequences: `core` stays pure; `ai` is reusable and can back a headless harness (the #24 "DeepSeek plays Minesweeper" idea); `ai` uses only external crates, so extracting it into its own crate later is cheap; the board / prompt / tools stay in the app (`ai_adapter`), not in `ai`; only the one-shot `suggest` mode is implemented now.
