# ProviderErrorKind is kept: config/upstream is a real pre-flight signal, not redundant

Issue #123 asked whether `ai::protocol::ProviderErrorKind` (`Config` / `Upstream`) holds independent meaning or is redundant, since the mid-stream `ai_adapter` refracts `Config` into `InterruptReason::Unknown` before it reaches a consumer. It is **not** redundant: the field is genuinely consumed, intact, on the pre-flight path. `ai_routes::preflight_response` returns a `ProviderError {kind,code,message}` body directly to the frontend on a `Guide::suggest` pre-flight failure, and `frontend/src/app/guideMode.ts`'s `providerAlertMessage` branches on that `kind` to show the player two materially different alerts — `config` → "AI 未配置：…", `upstream` → "AI 服务异常：…".

The classification is not arbitrary. It carries two paired axes that everything downstream depends on: **permanence** (will an unchanged retry ever succeed?) and **responsibility** (is it our setup/request, or the provider's service?). `Config` = permanent + ours (bad auth, unknown model, no provider, malformed request) — retrying is futile. `Upstream` = transient + theirs (network, rate limit, server error) — a backed-off retry usually succeeds. Those are exactly the inputs retry policy, circuit-breaking, and operator triage need.

The field is *not* derivable from `code` alone: `code` is `null` for several distinct failures — `Config` (no provider selected, unknown model, request serialization) and `Upstream` (transport / connect failure). Losing `kind` would merge "AI not configured" and "AI service down" into one player alert and one triage path.

Considered options: **drop** `ProviderErrorKind` and rely on `code` + `message` — rejected, because it loses the config/upstream distinction at pre-flight when `code` is `null`; **merge** the two-bucket `kind` into the finer `InterruptReason` taxonomy — deferred, because `InterruptReason` has no `Config` variant (config collapses to `Unknown` by design) and the pre-flight alert wants the distinct config/upstream pair; **status quo, keep** — accepted.

Consequences: the mid-stream `refract_provider_error` keeps its `Config -> Unknown` arm as a *defensive* contract. It is nearly unreachable in practice — DeepSeek returns unknown-model / serialization failures from `validate_model` pre-flight, and `SseState` only ever emits `Upstream` — but it is tested (`config_error_refracts_to_unknown`) and semantically correct (a config error that should never have streamed is reported as `Unknown`, not as a transient upstream failure). Future cleanup attempts must not treat it as dead code.
